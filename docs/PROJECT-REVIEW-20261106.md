# 当前项目缺陷与风险分析

日期：2026-11-06。对象：当前 Kotlin/Java 宿主、手机 UI 扩展、构建脚本及历史验收报告。只读代码审查，没有修改产品代码、操作用户聊天或重新运行真机测试。

结论：保留原版 SillyTavern 的路线符合产品目标。主要短板在安卓文件交互、故障恢复、长期性能和可复现交付；不需要因此重做聊天引擎。

## 优先处理

### 1. 聊天导出和整库备份的 Blob 下载未接通（已确认代码缺口）

`MainActivity.kt:117` 的下载监听只接受 `http://127.0.0.1:<端口>`，其余链接直接提示不支持。原版 `public/script.js:11535` 的聊天导出调用 `download`，该函数在 `public/scripts/utils.js:405` 使用 `URL.createObjectURL`；`public/scripts/user.js:279` 的账户备份也用 Blob URL。因此网页上的导出入口存在，并不代表安卓端能把相应文件保存出来。

系统备份又在 Manifest 中明确关闭。原版可能在应用内保存自动备份，但它不能抵御卸载或清空应用数据。优先补齐 Blob/data 下载桥接、整库导出/恢复和开发版到正式版迁移验收；备份默认排除 API Key。不能将“显示导出成功”当作文件可恢复。

### 2. 当前正式版缺少与版本绑定的完整真机验收（证据缺口）

`docs/RELEASE-1.2.6.md` 记录的是构建、Lint、签名、资源散列通过，并明确没有正式包真机功能验收。`artifacts/upstream/extensions-app/report.json` 对应较早开发包散列 `98469d…`。它证明当时样例通过，不能覆盖后续所有 UI 修改。

当前首页初始化为聊天列表，MainActivity 也已没有此前隐藏系统栏的调用。这些可能是用户主动改变的设计，不应自动回滚；但旧文档中“角色首页/全屏已验证”等描述已不能代表当前状态。建议每次发布以 APK 散列关联安装、冷启动、导出恢复、扩展、键盘、数据保留检查。

## 稳定性与兼容性

### 3. 长聊天优化依赖扩展开关，尚无长期性能结论（已确认依赖，影响待实测）

手机 UI 在首次启用时将原版 `chat_truncation` 调为 20，打开会话时按需重载；连续生成后的旧消息 DOM 清理依赖酒馆助手的 `better_message_to_load`。关闭该项或禁用助手后，不能保证持续保持 20 条。显示限制也不会缩小完整聊天数组、停止所有第三方脚本定时器或减少模型提示词计算。

已有 240 条合成样例通过，但没有本次最新版本长时间连续聊天、复杂 iframe、低内存设备的证据。应增加真实持续生成/滑动场景的帧耗时、内存和后台恢复测量，再决定是否需要宿主级策略；不要贸然删 DOM 破坏原版扩展事件。

### 4. 服务异常恢复较弱（代码确认，故障场景未复现）

`TavernService.kt:64–69` 使用 START_NOT_STICKY，健康检查只看 Node 进程是否存活。进程活着但 HTTP 不响应时不会被识别；异常退出主要要求用户重新启动。

`TavernRuntime.java:80–90` 首次随机分配端口并保存，后续不重新检查端口占用。若以后被其他进程占用，重试仍使用相同端口，可能持续启动失败。需补 HTTP 就绪检查、受控重启、端口冲突诊断；改变端口须考虑 WebView origin 和浏览器存储迁移。锁屏、省电模式下是否中断生成仍需真机验证，不能把前台通知当成永不被杀。

### 5. 升级后旧资源目录缺少回收机制（已确认）

`TavernRuntime.java:35` 按完整资源 SHA 新建 `server-<hash>`，未找到旧目录清理流程。只有完整上游资源包散列改变时才新增一份，不是每次修改 CSS 都复制。多次升级后可能积累多份源码和依赖。

内置扩展更新直接复制覆盖，也没有清理新版本已经移除的旧文件。建议使用临时目录、完整校验、切换完成标记，并保留一份可回滚版本后回收旧资源；始终排除用户数据目录。

### 6. UI 对原版 DOM 和扩展行为有耦合（已确认范围与具体边缘问题）

手机 UI 使用原版节点 ID、抽屉 class、事件和导出函数；原版或扩展升级时需要回归。`index.js:466–514` 将整个主文档的普通单选下拉框替换为底部面板，没有局限在手机导航自身。

该实现只检查 option 自身的 disabled/hidden，未继承 optgroup 的禁用/隐藏语义：若原版或扩展使用禁用分组，面板仍可能允许选择其中选项。这是可由代码确认的边缘缺陷，本轮未在真实功能页面复现。建议限定替换范围、补齐原生语义，不支持的控件回退原版。

此外，服务器插件、自动下载模型和可下载 tokenizer 在 `scripts/upstream/common.mjs` 中明确关闭。这是当前配置边界，不等于所有依赖这些能力的扩展都能直接使用。

## 工程与交付

### 7. 工程搬迁依赖本机目录链接（已确认）

约 8.3 GiB 工具、缓存和旧产物已实际移到 `D:\DevelopmentData\jiuguan`，工程保留 `.tools`、node_modules、app/build 等目录链接。这样当前电脑可继续构建，但复制源码到新电脑并不会自动拥有这些依赖；一些复制/统计工具还会跟随链接，继续显示很大的体积。

这次迁移属于存储位置整理，尚未完成便携化。需要新增外部工作目录配置和一键初始化，替代固定盘符、Codex Node 路径与目录链接依赖。正式签名也在外部 tools/signing，备份不能只复制工程源码。

### 8. 正式签名已完成，公开分发准备仍不完整（已确认交付边界）

`platform/upstream/runtime.lock.json` 表明安卓 Node 运行时来自第三方固定 APK 提取；有散列与来源记录，但本项目还没有完整的可复现运行时构建流程。SillyTavern/提示词模板使用 AGPL，内置酒馆助手为 PolyForm Noncommercial，公开分发或商业使用需要按对应许可处理，不能把“成功签名”视为这些工作全部完成。

建议补齐构建来源/补丁/许可交付材料，明确非商业组件边界。32 位及 x86 未构建，仅支持 arm64；Android 8–15 的设备覆盖也未完成。

## 建议顺序

1. 导出、备份恢复、正式版数据迁移与版本绑定验收。
2. 长聊天性能测量、服务异常恢复与端口冲突处理。
3. UI 控件兼容、扩展升级回归及旧资源回收。
4. 外部依赖初始化、签名离线备份、可复现构建与分发材料。

已具备的基础：原版内核、数据与资源分离、解压路径校验、固定来源与散列、正式包关闭 WebView 调试、生成/保存期间限制切换。没有证据支持“架构必须推倒重做”，也没有把未复现的风险描述成已经发生的数据丢失。
